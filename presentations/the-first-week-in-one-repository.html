The First Week
in One Repository

Seven steps, in the order I would do them. Every one is a file in the repository or a setting on it, except the last, which is half an hour a month.

From the exploration What Is the Second Pair of Eyes For? · chapter 05

Build to Understand

Why this list

Most of the argument is somebody else's decision

Chapter 04 was the order for a company. A developer who agrees with all of it still has to do something on Monday, in one repository.

This is the same order narrowed to the files and settings in front of one person. Nothing here needs a platform team, a budget, or a vendor.

Build to Understand
01

Step 1

Decide what this repository touches

Chapter 04 tiered whole repositories and never said who does the tiering. This repository needs its own answer first, because the answer decides how strict the rest of the list should be.

  • Answer one question: does it move money, hold customer data, or neither?
  • Write the answer in the README, under a short “Review rules” heading, with the date
  • Say what follows: how many reviewers, whether a machine may approve, whether a security review is mandatory
  • Revisit it when the repository starts touching something new

One sentence in the README that a new joiner can find is more than most repositories have today.

Build to Understand
02

Step 2

Make the mechanical checks run on every change

Everything mechanically verifiable runs before a person looks at the change.

  • Formatting and linting, in a workflow file under .github/workflows/
  • The test suite, in the same file
  • A static analysis pass, in the same file
  • Dependency scanning, in .github/dependabot.yml
  • Secret scanning, a toggle in the repository settings

Google's reason, quoted in chapter 03: static analysis exists so that human review can “focus on issues that are not mechanically verifiable.”

Build to Understand
03

Step 3

Make the checks from step 2 block a merge

A check that runs is a suggestion. A check that blocks a merge is a control. This is the step that gets skipped.

  • Require the formatter, the linter, the tests and the static analysis pass, each by name
  • Require a pull request before merging
  • Stop direct pushes to the default branch
  • Dismiss stale approvals when new commits land

All four live in branch protection, or in a ruleset. Dismissing stale approvals makes an approval refer to the code that actually merges.

Build to Understand
04

Step 4

Name the owners of the paths that carry risk

Step 1 settled what the whole repository touches. Some paths inside it carry more than the rest, and that difference fits in a file.

  • List the paths that move money or hold customer data
  • Give each a named reviewer or team
  • Leave the rest on the lighter default
  • Switch on “require review from code owners”, or the file only suggests
# .github/CODEOWNERS
# Everything, unless a later line overrides it.
*                     @payments-team

# The paths that move money.
/src/settlement/      @settlement-owners @security
/src/ledger/          @settlement-owners

# Anything that changes how the service is deployed.
/.github/workflows/   @platform

The last matching line wins, so the catch-all goes first and the risky paths underneath it.

Build to Understand
05

Step 5

Decide, in writing, whether a machine may approve here

A setting with no owner is a decision nobody made. The README is the answer to where. The reason is the answer to why there.

  • Decide whether a machine review counts toward required approvals
  • Add it to the same “Review rules” heading step 1 started
  • Give the reason, not only the answer
  • Revisit it when what the repository touches changes
## Review rules
Touches: customer money, through settlement
and the ledger. 2026-09-28

Machine approval: not allowed here. A machine
approval would be the only approval on a
change that moves money, and nothing logs
that it happened. 2026-09-28

The setting has nowhere to hold a reason, and nothing logs a machine approval. The README is where the decision survives.

06

Step 6

Ask the author for what no check can see

One template, the same questions in front of every change. The second heading is the load-bearing one, and it is the half most templates leave out.

  • What changed, and why it belongs here
  • What you want looked at, specifically
  • How to undo it
  • Which parts an agent wrote

07

Step 7

Watch for the day the approvals stop meaning anything

Steps 1 to 6 can all be in place and still stop working, and nothing announces it. The checks stay green, the approvals keep arriving, the template keeps getting filled in, and none of that requires anyone to have read the change.

Once a month, read ten merged pull requests and ask what you are seeing:

  • Approvals that arrived a minute after opening, on changes too long to read in a minute
  • Template sections filled with “N/A”, the branch name, or the commit message pasted back
  • The same person approving everything, including the parts they do not work on
  • Code owners approving paths they have never otherwise touched

No setting reports any of this. Somebody has to go and look.

What the list cannot do

It makes the decision cheaper to reach.
It does not make the decision.

Steps 2 to 4 make the judgement cheaper to reach. Step 6 gives the decider something to read. Step 7 checks that the decision is still being made. None of them decides whether the change is wanted.

And I have not run this list against our own repositories. I do not know how many of these settings are already on, which makes step 3 the first thing I owe the argument.
