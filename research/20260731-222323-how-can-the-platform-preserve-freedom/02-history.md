## Long arc

The modern platform story begins with turning infrastructure from a ticket queue into an API. On 2006-08-24, Amazon announced the EC2 beta as a web service through which developers could obtain and configure compute in minutes, scale it up or down, and pay for what they used. That created real self-service, but the interface also made one provider's resource model the application team's operating environment; freedom from an internal operations queue was not the same thing as freedom from the provider. Heroku's Twelve-Factor methodology later tried to recover portability at the application boundary by separating code, configuration, backing services, build, release, and run; Heroku described the method on 2013-08-15 as designed for both developer productivity and “maximum portability” across platforms ([AWS](https://aws.amazon.com/about-aws/whats-new/2006/08/24/announcing-amazon-elastic-compute-cloud-amazon-ec2---beta/), [Heroku](https://www.heroku.com/blog/twelve-factor-apps/)).

As systems became distributed, organizations moved repeated operational decisions out of applications and into shared traffic layers. Netflix open-sourced Zuul on 2013-06-12 after using it as the edge of an API serving more than 1,000 device types; its ordered filters centralized routing, resilience, security, and measurement while leaving feature teams able to deploy adapter logic. Lyft released Envoy on 2016-09-14 after using it first as an edge proxy during its monolith-to-microservices migration; Envoy's API-driven configuration and rich telemetry then made the same data plane useful for service meshes. These gateways created leverage by moving cross-cutting work to a reusable choke point, but they also concentrated failure and policy power there ([Netflix](https://medium.com/netflix-techblog/announcing-zuul-edge-service-in-the-cloud-ab3af5be08ee), [CNCF Envoy journey report](https://www.cncf.io/reports/envoy-project-journey-report/), [Envoy Gateway history](https://www.cncf.io/blog/2022/05/16/introducing-envoy-gateway/)).

Containers and Kubernetes shifted the portability boundary again. Kubernetes' first commit landed on 2014-06-06 and the project reached version 1.0 on 2015-07-21; an open orchestration API separated application scheduling from any one cloud, while interfaces for runtimes and plugins eventually enabled more implementation choice. Yet Kubernetes also accumulated provider-specific and historical integrations inside its core. The later removal of dockershim and extraction of in-tree cloud-provider code show the recurring correction: preserve the stable contract, move replaceable integrations behind it, and make the migration explicit rather than keeping every compatibility path forever ([Kubernetes ten-year history](https://kubernetes.io/blog/2024/06/06/10-years-of-kubernetes/), [dockershim FAQ](https://kubernetes.io/blog/2022/02/17/dockershim-faq/), [cloud-provider externalization](https://kubernetes.io/blog/2023/12/14/cloud-provider-integration-changes/)).

The next wave treated policy, telemetry, and developer experience as platforms. Open Policy Agent entered the CNCF Sandbox on 2018-03-29 as a general-purpose engine intended to separate policy decisions from hard-coded service logic. OpenTracing and OpenCensus merged into OpenTelemetry on 2019-05-21 because two similar but incompatible standards created confusion; the merger prioritized bridges and an orderly transition over a clean-sheet rewrite. Spotify released Backstage on 2020-03-16, then made its template contribution model explicit on 2020-08-05: teams could inherit organizational defaults while proposing their own templates through code review. These cases point to a workable autonomy bargain—centralize the interface and shared controls, but keep implementations, plugins, and contribution paths open ([OPA](https://www.cncf.io/blog/2018/03/29/cncf-to-host-open-policy-agent-opa/), [OpenTelemetry](https://www.cncf.io/blog/2019/05/21/a-brief-history-of-opentelemetry-so-far/), [Backstage introduction](https://backstage.io/blog/2020/03/18/what-is-backstage/), [Backstage templates](https://backstage.io/blog/2020/08/05/announcing-backstage-software-templates/)).

Platform engineering subsequently named this pattern “golden paths” or “paved roads,” but the evidence has always included a warning. DORA's report published on 2024-10-22 found internal platforms associated with higher developer productivity while also identifying an initial performance dip and the need for user-centered design and developer independence. Thoughtworks had already warned on 2018-05-15 that “generic cloud” layers often become expensive lowest-common-denominator abstractions; it recommended comparing exit cost with the benefit of provider-specific capabilities rather than pursuing portability at any cost. The historical lesson is therefore narrower than “standardize” or “do not standardize”: standardize the smallest interface that removes repeated work, budget for its operators and migrations, and treat a usable escape route as a maintained capability ([DORA](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report?hl=en), [Thoughtworks](https://www.thoughtworks.com/radar/techniques/generic-cloud-usage), [CNCF Platforms White Paper](https://tag-app-delivery.cncf.io/es/whitepapers/platforms/)).

AI gateways are the newest pass through the same cycle. Cloudflare's AI Gateway beta on 2023-09-27 put caching, rate limits, retries, analytics, and model fallback between applications and model providers; Anthropic's Model Context Protocol on 2024-11-25 proposed an open contract for connecting assistants to tools and data. The old pattern is a gateway plus an integration standard. What changes the stakes is that a fallback can change model behavior, an agent can take consequential actions, indirect prompt injection can redirect those actions, and providers routinely version or retire models—so portability now requires behavioral evaluation and permission containment, not merely API compatibility ([Cloudflare](https://blog.cloudflare.com/announcing-ai-gateway/), [Anthropic](https://www.anthropic.com/news/model-context-protocol), [NIST agent-hijacking research](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations), [OpenAI model/API updates](https://openai.com/index/function-calling-and-other-api-updates/)).

| 2019-05-21 | **OpenTelemetry** — OpenTracing, OpenCensus, Google, LightStep, Microsoft, Uber, and CNCF | Two overlapping telemetry standards agreed to merge, provide compatibility bridges, and put their predecessor projects into read-only mode. | OpenTelemetry moved to CNCF Incubating status on 2021-08-26 and Graduated status on 2026-05-11. | The ecosystem converged on vendor-neutral instrumentation, making backend replacement more plausible without re-instrumenting every application ([merger history](https://www.cncf.io/blog/2019/05/21/a-brief-history-of-opentelemetry-so-far/), [CNCF project record](https://www.cncf.io/projects/opentelemetry/)). |
| 2020-03-18 | **Backstage** — Spotify platform engineers, Spotify application teams, and later CNCF contributors | Spotify explained the open-source release made two days earlier: a plugin-based developer portal that tied together a fragmented infrastructure landscape. | Backstage exposed an extensible catalog and templates rather than replacing every underlying tool; Spotify invited external collaboration while retaining specialized internal plugins. | Its 2020-08-05 template design made the autonomy mechanism concrete: standards were code, and teams with different needs could contribute alternatives through pull requests ([Backstage introduction](https://backstage.io/blog/2020/03/18/what-is-backstage/), [templates](https://backstage.io/blog/2020/08/05/announcing-backstage-software-templates/)). |
| 2021-04-12 | **OpenSearch** — Elastic, AWS, users, and later the OpenSearch community | AWS introduced an Apache-licensed fork after Elastic changed Elasticsearch and Kibana from Apache 2.0 to SSPL/Elastic licensing. | OpenSearch shipped a 1.0 release on 2021-07-12 with a compatibility setting for clients performing version checks and continues to publish releases. | Source availability alone proved insufficient as an exit guarantee; a permissive pre-change codebase, compatible client surface, trademark separation, and funded maintainers made the fork practical. Elastic disputed AWS's framing and said its change protected investment from cloud providers selling the software without contributing back ([Elastic](https://www.elastic.co/blog/licensing-change), [AWS](https://aws.amazon.com/blogs/opensource/introducing-opensearch/), [OpenSearch versions](https://docs.opensearch.org/latest/version-history/)). |
| 2022-05-03 | **Kubernetes dockershim removal** — Kubernetes SIG Node, Docker, Mirantis, containerd, and CRI-O | Kubernetes removed its built-in Docker Engine shim after a deprecation period; users could move to CRI-compatible runtimes or an external `cri-dockerd` adapter. | The core shed a maintenance burden while Docker workflows could continue through a separately owned adapter. | The episode established a useful exit pattern: publish a narrow runtime interface, give notice, provide migration guides and alternatives, then remove the exceptional integration from the platform core ([release](https://kubernetes.io/blog/2022/05/03/kubernetes-1-24-release-announcement/), [FAQ](https://kubernetes.io/blog/2022/02/17/dockershim-faq/)). |
| 2023-09-05 | **OpenTofu** — HashiCorp, Gruntwork, Spacelift, Harness, Env0, Scalr, and the Linux Foundation | After HashiCorp moved future Terraform releases to the Business Source License, the OpenTF group published a fork of the last open-source code line; it later became OpenTofu under Linux Foundation governance on 2023-09-20. | OpenTofu positioned itself as a drop-in Terraform replacement and retained access to the provider and module ecosystem. | Compatibility plus neutral governance gave users and ecosystem vendors an exit route, while subsequent divergence means freedom now depends on sustaining both the implementation and its surrounding registry ecosystem ([OpenTofu fork](https://opentofu.org/blog/the-opentofu-fork-is-now-available/), [Linux Foundation](https://www.linuxfoundation.org/press/announcing-opentofu), [HashiCorp's position](https://www.hashicorp.com/en/blog/hashicorp-updates-licensing-faq-based-on-community-questions)). |
| 2023-09-27 | **Cloudflare AI Gateway** — Cloudflare, model providers, and AI application teams | Cloudflare launched a proxy that could observe, cache, rate-limit, retry, and route AI API requests, including fallback between providers. | A familiar gateway pattern was applied to model traffic with only a base-URL change for supported APIs. | Governance and cost controls gained a central enforcement point, but routing and fallback now had the power to alter application behavior by changing the model ([Cloudflare](https://blog.cloudflare.com/announcing-ai-gateway/)). |
| 2024-11-25 | **Model Context Protocol** — Anthropic, tool/data providers, assistant builders, and open-source contributors | Anthropic open-sourced a client-server standard for connecting AI assistants to repositories, business tools, and development environments. | The launch provided reference SDKs and prebuilt servers, turning repeated point-to-point integrations into a shared protocol. | MCP is a direct precedent for the chapter's contract-first idea, but it standardizes connectivity rather than the full agent lifecycle, governance, or behavioral portability ([Anthropic](https://www.anthropic.com/news/model-context-protocol)). |

## Failed attempts at the same thing

1. **rkt: open standards and composability were not enough to sustain a second runtime.** CoreOS created rkt as a secure, composable, standards-oriented container engine; CNCF accepted it on 2017-03-29, then archived it on 2019-08-16 after adoption, project activity, and contributor numbers declined and CVEs went unpatched. The failure factor was not a bad interface alone but insufficient ongoing demand and ownership beside containerd and CRI-O. That factor is still present for AI-platform adapters: every additional “choice” needs maintainers, release compatibility, vulnerability response, and actual users ([CNCF archive notice](https://www.cncf.io/blog/2019/08/16/cncf-archives-the-rkt-project/)).

2. **Istio Mixer: a maximally extensible central policy/telemetry hop imposed too much runtime cost and operational surface.** Istio deprecated Mixer on 2020-03-05 and removed it on 2020-11-19, replacing out-of-process telemetry with in-proxy extensions. Istio reported that the new path reduced 90th-percentile latency from 7 ms to 3.3 ms and cut CPU consumption by 50% to 0.55 vCPU per 1,000 requests per second; it also consolidated separate control-plane microservices into `istiod` after operators said independent rollout and scaling did not justify the orchestration cost. The same factors remain present for an AI gateway: an abstract extension layer can become the dominant latency, debugging, and reliability burden, and a separately scaled microservice is not free just because it is reusable ([Istio 1.5](https://istio.io/latest/news/releases/1.5.x/announcing-1.5/), [Istiod rationale](https://istio.io/latest/blog/2020/istiod/), [Istio 1.8](https://istio.io/latest/news/releases/1.8.x/announcing-1.8/)).

3. **Kubernetes Service Catalog/Open Service Broker API: a common managed-service abstraction failed to earn enough adoption.** The Kubernetes Service Catalog tried to translate Kubernetes resources into the Open Service Broker API so applications could provision and bind managed services through one model. Its repository was archived on 2022-05-06; Couchbase later withdrew its broker, stating on 2023-08-01 that the expected uptake had not occurred and related projects had been withdrawn or ended. The factors are still present: cloud and model providers expose differentiated capabilities faster than a common schema evolves, while users have little incentive to adopt an extra broker when provider-native APIs or operators are easier ([archived repository](https://github.com/kubernetes-retired/service-catalog), [Couchbase withdrawal](https://www.couchbase.com/blog/withdrawal-service-broker/)).

4. **dockershim: a compatibility adapter became permanent platform debt.** Kubernetes added dockershim because Docker Engine did not implement the later Container Runtime Interface; the project says the shim was intended to be temporary but became a heavy maintainer burden and blocked work on features incompatible with it. Removal on 2022-05-03 succeeded because a narrower standard interface, alternative runtimes, an external adapter, a deprecation policy, surveys, and migration documentation existed. AI platforms will reproduce the failure if the core permanently owns a special adapter for every provider rather than defining ownership and deletion conditions at the start ([Kubernetes FAQ](https://kubernetes.io/blog/2022/02/17/dockershim-faq/), [migration commitments](https://kubernetes.io/blog/2022/01/07/kubernetes-is-moving-on-from-dockershim/)).

5. **“Any-cloud” abstraction: portability pursued everywhere becomes a lowest-common-denominator product.** This is a repeated strategy rather than one named shutdown. Thoughtworks reported on 2018-05-15 and 2018-11-14 that organizations were making large investments in home-grown cross-cloud layers that were expensive to maintain and prevented use of differentiated provider capabilities; it recommended explicit, risk-based exit planning instead. The issue is more acute for models because a provider's tool calling, context limits, safety behavior, latency, and model quality are not interchangeable just because requests can share a JSON shape ([Thoughtworks](https://www.thoughtworks.com/radar/techniques/generic-cloud-usage), [OpenAI API stability/deprecation note](https://openai.com/index/function-calling-and-other-api-updates/)).

## Recurring cast

## What's actually new this time

**Genuinely new or materially intensified:**

- **The platform mediates decisions, not only deterministic requests.** An API gateway usually routes bytes to a service with known semantics. An AI gateway may retry a prompt against a different model or cache an answer; Cloudflare exposes both fallback and caching, so an apparently infrastructural choice can change quality, safety, latency, cost, or reproducibility ([Cloudflare](https://blog.cloudflare.com/announcing-ai-gateway/)).
- **Agents can convert untrusted content into actions.** NIST's agent-hijacking work found that indirect prompt injection can cause an agent ingesting attacker-controlled data to take unintended harmful actions. “Enforce at the last system that can prevent harm” is therefore harder than it was for deployment policy: the harmful path may traverse model reasoning, tool authorization, data access, and an external side effect ([NIST](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations)).
- **Behavioral portability is separate from syntactic portability.** OpenAI promises stability for pinned model identifiers while also documenting deprecations and model transitions; two providers accepting similar message JSON do not guarantee equivalent tool selection, refusals, output structure, or evaluation scores. A credible exit test must run workflow-specific evaluations, not merely swap a base URL ([OpenAI](https://openai.com/index/function-calling-and-other-api-updates/), [NIST Generative AI Profile](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)).
- **The contract surface now spans tools and authority.** MCP standardizes assistant connections to tools and data, but the act of discovering and invoking tools creates credential, consent, and least-privilege questions beyond an ordinary service catalog. The standard reduces connector duplication; it does not by itself decide which actions are authorized or how an organization proves control effectiveness ([Anthropic](https://www.anthropic.com/news/model-context-protocol)).
- **The upstream market changes at model cadence.** Provider-specific models and capabilities can be introduced, revised, pinned, and retired faster than traditional infrastructure interfaces. That makes adapter ownership, conformance tests, and planned degradation modes first-order platform features rather than maintenance details ([OpenAI](https://openai.com/index/function-calling-and-other-api-updates/), [Anthropic deprecation policy](https://platform.claude.com/docs/en/about-claude/model-deprecations)).

**Old pattern, new branding:**

- A model gateway is still an API gateway: one control point for authentication, rate limits, retries, routing, telemetry, and spend ([Netflix Zuul](https://medium.com/netflixtechblog/announcing-zuul-edge-service-in-the-cloud-ab3af5be08ee), [Cloudflare AI Gateway](https://blog.cloudflare.com/announcing-ai-gateway/)).
- A versioned agent contract in a repository is still contract-as-code plus CI policy, with precedents in Twelve-Factor conventions, Kubernetes declarative APIs, OPA, and Backstage templates ([Heroku](https://www.heroku.com/blog/twelve-factor-apps/), [OPA](https://www.cncf.io/blog/2018/03/29/cncf-to-host-open-policy-agent-opa/), [Backstage](https://backstage.io/blog/2020/08/05/announcing-backstage-software-templates/)).
- “Golden path, not cage” is not a novel AI principle. Spotify explicitly tied open pull requests for new templates to the balance between autonomy and standardization on 2020-08-05; CNCF later made extensibility and platform-as-product part of its platform guidance ([Backstage](https://backstage.io/blog/2020/08/05/announcing-backstage-software-templates/), [CNCF maturity model](https://www.cncf.io/blog/2023/11/20/announcing-the-platform-engineering-maturity-model/)).
- Vendor escape still depends on boring assets: open formats, exportable state, compatible interfaces, bridges, alternative operators, deprecation windows, and someone funded to maintain the destination. OpenTelemetry, OpenSearch, OpenTofu, Dropbox, and dockershim all demonstrate a different subset of that same migration machinery ([OpenTelemetry](https://www.cncf.io/blog/2019/05/21/a-brief-history-of-opentelemetry-so-far/), [OpenSearch](https://aws.amazon.com/blogs/opensource/introducing-opensearch/), [OpenTofu](https://opentofu.org/blog/the-opentofu-fork-is-now-available/), [Dropbox](https://dropbox.tech/infrastructure/magic-pocket-infrastructure), [Kubernetes](https://kubernetes.io/blog/2022/02/17/dockershim-faq/)).

## What an experienced observer would expect next

1. **The first useful version will be smaller than the first architecture diagram.** DORA recommends starting with a minimum viable platform around one common workflow, and both Kubernetes and Backstage were released before their broader visions were complete. An experienced platform builder would expect a repository contract, CI validation, provider credentials, and existing telemetry to precede a bespoke runtime or portal ([DORA capability guidance](https://dora.dev/capabilities/platform-engineering/), [Kubernetes history](https://kubernetes.io/blog/2018/07/20/the-history-of-kubernetes-the-community-behind-it/), [Backstage](https://backstage.io/blog/2020/03/18/what-is-backstage/)).

2. **The happy path will attract demand for exceptions, then plugins.** Backstage's answer was to make templates code and invite pull requests; Envoy and OPA separated a stable core from extensions and enforcement placements. If the agent contract is successful, teams will quickly request provider-specific fields, custom tools, alternative evaluators, and framework adapters. The decisive governance question will be who can add them, not whether the schema is technically extensible ([Backstage templates](https://backstage.io/blog/2020/08/05/announcing-backstage-software-templates/), [Envoy history](https://www.cncf.io/blog/2022/05/16/introducing-envoy-gateway/), [OPA](https://www.cncf.io/blog/2018/03/29/cncf-to-host-open-policy-agent-opa/)).

3. **Provider semantics will leak through the abstraction.** Thoughtworks' generic-cloud warning and the Service Catalog's weak uptake both show that common interfaces lose pressure against differentiated vendor features. The likely stable shape is a portable core plus declared capability extensions, not perfect interchangeability; exit tests should record which workflow properties degrade when a model or vendor changes ([Thoughtworks](https://www.thoughtworks.com/radar/techniques/generic-cloud-usage), [Couchbase](https://www.couchbase.com/blog/withdrawal-service-broker/)).

4. **A gateway will appear once cost, incident response, or policy needs outweigh direct-call simplicity.** Zuul, Envoy, and Cloudflare AI Gateway all emerged because many clients repeating routing, resiliency, security, and telemetry work created system-wide burden. The experienced move is to add the gateway only for controls that need a traffic choke point, while leaving repository-time checks and workflow decisions outside it ([Netflix](https://medium.com/netflixtechblog/announcing-zuul-edge-service-in-the-cloud-ab3af5be08ee), [Envoy](https://www.cncf.io/reports/envoy-project-journey-report/), [Cloudflare](https://blog.cloudflare.com/announcing-ai-gateway/)).

5. **The platform will initially slow some teams down.** DORA observed a potential performance dip as platforms mature, and Kubernetes' dockershim survey found more than 600 respondents with remaining migration dependencies, some outside their control. A credible rollout will publish the dip, exception lead time, support load, and work shifted to consumers rather than presenting adoption as proof of productivity ([DORA](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report?hl=en), [Kubernetes migration commitments](https://kubernetes.io/blog/2022/01/07/kubernetes-is-moving-on-from-dockershim/)).

6. **The first overgeneralized component will eventually be removed or moved out of core.** Mixer, dockershim, and in-tree cloud providers each started as convenient shared integration and later became performance, maintenance, or release-coupling liabilities. An experienced observer would expect the AI platform to externalize adapters and perhaps policy evaluators once their change cadence or ownership differs from the contract core ([Istio](https://istio.io/latest/news/releases/1.5.x/announcing-1.5/), [dockershim](https://kubernetes.io/blog/2022/02/17/dockershim-faq/), [cloud-provider externalization](https://kubernetes.io/blog/2023/12/14/cloud-provider-integration-changes/)).

7. **A real exit will require a funded destination, not a clause saying “portable.”** Dropbox built and operated its own storage estate; OpenSearch and OpenTofu had code, compatible interfaces, institutional sponsors, and maintainers; rkt had an open standard but declining users and contributors. A practical freedom test therefore includes an alternative implementation, exportable state, a migration rehearsal, operational ownership, and a supported fallback period ([Dropbox](https://dropbox.tech/infrastructure/magic-pocket-infrastructure), [OpenSearch](https://aws.amazon.com/blogs/opensource/introducing-opensearch/), [OpenTofu](https://www.linuxfoundation.org/press/announcing-opentofu), [rkt](https://www.cncf.io/blog/2019/08/16/cncf-archives-the-rkt-project/)).

8. **Governance will become as important as architecture if adoption succeeds.** OpenTelemetry resolved a split through shared governance and compatibility bridges; OpenTofu and OpenSearch arose when vendor licensing changed; CNCF hosts multiple platform components to reduce dependence on their originating companies. If the agent contract becomes organizational infrastructure, teams will eventually ask who can change it, veto extensions, grant exceptions, fund adapters, and retire the platform ([OpenTelemetry](https://www.cncf.io/blog/2019/05/21/a-brief-history-of-opentelemetry-so-far/), [Linux Foundation](https://www.linuxfoundation.org/press/announcing-opentofu), [CNCF Platforms White Paper](https://tag-app-delivery.cncf.io/es/whitepapers/platforms/)).
